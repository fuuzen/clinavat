# 账号与槽位

**槽位**是一个已登录的官方 CLI 账号。每个槽位只对应一种 CLI（Claude Code 或 Codex），创建后不能更改；同一个人要同时用两种 CLI，就需要两个槽位。管理员把槽位分配给成员，成员在对话中选择用哪个槽位。

## 管理用户

管理员从侧栏头像进入「管理面板」：

- **用户与权限**：点击「创建用户」，填写用户名和至少 12 位的初始密码。新用户是普通成员；这不受 `CLINAVAT_REGISTRATION` 开关影响，也不会切换管理员自己的登录。初始密码请通过可信渠道交给成员。
- **Workspaces / 开发机连接**：可以切换到任意用户，只读查看其项目、开发机和每个项目的对话数量。创建、编辑或测试连接需要切回自己的账号。

需要开放自助注册时，设置 `CLINAVAT_REGISTRATION=true` 并重启 Hub。无论哪种方式，**新用户都没有槽位权限**，管理员自己也需要显式分配。没有槽位的用户可以管理开发机和项目，但无法启动智能体。

## 创建并登录槽位

1. 在「管理面板 → 槽位管理」创建槽位，例如 `slot_claude_01`，选择 `claude` 或 `codex`。
2. 在服务器上，以运行 Hub 的系统用户、使用该槽位的 HOME 目录完成官方登录。管理界面会显示实际目录和登录命令。Docker 部署的示例：

   ```bash
   docker compose exec -e HOME=/srv/clinavat/slots/slot_claude_01 \
     -e CLAUDE_CONFIG_DIR=/srv/clinavat/slots/slot_claude_01/.claude \
     hub claude auth login
   docker compose exec -e HOME=/srv/clinavat/slots/slot_codex_01 \
     -e CODEX_HOME=/srv/clinavat/slots/slot_codex_01/.codex \
     hub codex -c 'cli_auth_credentials_store="file"' login --device-auth
   ```

   重新登录前，先停止所有正在使用该槽位的任务。目前支持 Claude Code 的 claude.ai OAuth 登录和 Codex 的文件方式认证。
3. 在槽位卡片上点击用户选择框，搜索并选择一位成员即保存；选择「未分配」则取消分配。一个用户可以拥有多个槽位。早期版本中多人共享的槽位会显示“待整理”，需要管理员手动选择一位使用者。
4. 卡片右上角的开关用于启用 / 停用槽位；正在使用的槽位要等任务结束后才能调整。

### 槽位状态

| 状态 | 含义 |
| --- | --- |
| `IDLE` | 可以使用 |
| `RATE_LIMITED` | 管理员标记为额度受限，阻止新任务 |
| `DISABLED` | 已停用，阻止新任务 |

“是否正在被使用”单独显示。这些状态只由管理员设置：系统会显示账号额度，但**不会**根据额度自动修改状态、排队、换账号或重试。修改使用权限也不会重置受限或停用状态。

## 在对话中使用槽位

- **新对话**：从自己有权限的槽位中选择一个，对话的 CLI 类型随槽位确定。
- **切换账号**：已有对话可以在输入框切换到另一个**同类型**的槽位，从下一轮开始生效。切换后会清除模型和思考强度的选择，并重新读取新账号可用的模型。Claude 对话不能切换为 Codex 对话。
- **运行中不能切换**：先点击停止，等 CLI 退出、状态清理完成后再切换。切换只影响当前对话，其他对话不受影响。
- **跨账号恢复**：切换后继续使用原来的原生会话 ID。新账号需要具备对应的模型、组织策略和资源权限，否则官方 CLI 可能拒绝恢复。失败的一轮不会自动重试。

### 同时使用的规则

- 一个槽位同一时间**只能被一位用户使用**；读取模型列表也算作使用。
- 同一用户可以同时运行多个对话，使用相同或不同的槽位都可以。
- 其他用户需要等这个槽位的所有任务和模型查询结束后才能使用，否则会收到冲突提示。
- 同一项目中并行的对话操作的是同一个目录，文件修改可能互相影响；需要隔离时请使用不同项目。修改或删除项目需要等该项目的所有对话停止。

### 撤销权限

撤销用户的权限或停用槽位时，需要等该槽位上的任务和模型查询全部结束。对话和原来的选择记录会保留，但后端会拒绝继续使用已撤销的槽位；旧页面提交过期的设置会被拒绝并刷新。

## 额度显示

槽位卡片和输入框的槽位菜单会显示各个额度窗口的已用 / 剩余百分比、重置倒计时、更新时间和查询状态。槽位图标外圈表示主额度（优先显示每周总额度），内圈表示 5 小时窗口（仅在服务端提供时显示）。未知、过期或查询失败的窗口显示为虚线，不会当作 0%。

**数据来源**：只采用账号服务端返回的数据，不根据 Token 消耗推算。Claude Code 通过控制协议 `get_usage`（实验接口）读取，Codex 通过 app-server 的 `account/rateLimits/read` 读取（含积分余额）。“额度受限”只来自服务端的明确信号。

**更新时机**：

- 对话运行中收到 CLI 的额度事件时立即推送；Codex 对话启动时会额外读取一次。
- 相关页面可见时每 90 秒补查一次，同一网页的多个位置共用一次查询；页面重新可见时也会补查。
- 后端对同一槽位至少间隔 60 秒才查询一次，手动刷新至少间隔 15 秒，全局最多同时 2 个查询；停用的槽位不查询。Claude Code 自身有约 60 秒缓存。

**查询方式**：查询在 `run/usage-probes/` 下的临时 HOME 中进行，只放入槽位授权文件的副本，不占用槽位，结束后删除。如果查询期间 CLI 刷新了令牌，仅在槽位授权文件没有被改动时写回。槽位正在使用时，只有访问令牌离过期还有 15 分钟以上才查询，以免和运行中的 CLI 同时刷新令牌。

**数据有效期**：额度数据只保存在 Hub 内存中，重启后重新查询。超过 15 分钟没有更新或最近一次查询失败时显示“数据已过期”。数据按账号标识绑定，槽位改登录其他账号后旧数据会被清除。倒计时归零只表示“已到重置时间，待刷新确认”，不代表额度已经恢复。

## 凭据与会话数据存放

| 内容 | 位置 |
| --- | --- |
| 槽位授权 | 槽位 HOME 下的 `.claude` 或 `.codex`，始终留在槽位内，不按对话复制 |
| 用户的原生会话 | `users/<user-id>/engine-state/<engine>/`，使用槽位时以目录链接接入 |
| 用户在某槽位的运行配置 | `users/<user-id>/slot-state/<slot-id>/runtime` |
| Codex Goal 数据库 | `users/<user-id>/engine-state/codex/goals_1.sqlite` |

因为会话数据按用户保存，同一用户换槽位后仍能继续原来的对话。每一轮都会记录实际使用的槽位和凭据版本。CLI 的命令行输入历史不会跨槽位共享，Codex 的本地索引也按槽位独立保存。令牌刷新仍由官方 CLI 决定，平台无法保证提供方不会让令牌失效。

**槽位交给另一位用户前**，系统会断开上一位用户的会话目录，并清理运行缓存和索引，防止后来者看到之前的历史。系统只接入明确支持的会话目录，不复制运行中的 SQLite / WAL 文件。

## 故障处理

- **槽位交接日志**：位于 `accounts/slot-runtime/<slot-id>.json`。如果后台进程没有退出、配置不匹配或清理失败，日志会保留，槽位不会交给其他用户；未完成的恢复会阻止 Hub 启动。处理时先停止相关进程，备份槽位、用户状态和日志，根据错误信息修复后重启。**不要直接删除日志来绕过检查。**
- **首次接管时的旧数据**：无法确定归属的旧运行状态保存在 `backups/slot-runtime-v3/<slot-id>/runtime`，初始化记录在 `accounts/slot-profiles-v3/<slot-id>.json`。
- **CLI 生成的账号备份文件**：CLI 自己产生的配置备份、以及写入中断留下的临时文件，会归档到 `backups/slot-account-artifacts/<slot-id>/`。其中可能包含登录凭据，应像槽位授权一样保护。

多人共用一个订阅账号还需遵守提供方的账号与席位条款。
