# 虚拟机隔离

> 状态：已完成运行系统从宿主机到虚拟机的切换，并验证真实 Claude/Codex 对话、审批、原生会话恢复、开发机同步和文件预览；Claude 另验证了暂停、继续、暂停后停止和槽位再租用。默认配置仍为宿主机模式，用 `CLINAVAT_EXECUTION_HOST=lxd` 开启。
>
> 宿主机模式**只适用于单一、受信任的使用者**：智能体命令与 Hub 是同一个系统用户，可以读取数据目录和 `.env`。

## 目标

- 每个用户的 CLI、workspace 和 SSH 凭据运行在该用户专属的虚拟机中，用户之间互相隔离。
- workspace 仍保存在宿主机存储上，通过 virtiofs 挂载进虚拟机。
- 上游网关合并到本机虚拟化环境统一管理。

## 架构

```text
浏览器 ─ Web 入口 ─ Hub（宿主机，受信任）
                     │  ExecutionHost
          ┌──────────┴──────────┐
   ProcessExecutionHost    LxdExecutionHost
   宿主机进程              lxc exec + 受限证书（仅 clinavat 项目）
                                │
        ┌───────────────────────┼───────────────────────┐
   槽位 VM（每个槽位一台）  用户工作区容器（每个用户一个）  网关 VM（独立项目）
   CLI、额度查询、登录      Mutagen 同步
        │                       │
        └── 同步屏障经 Hub 中继 ─┘
```

- 所有为用户启动进程的代码都经过 `backend/src/execution/types.ts` 的 `ExecutionHost`，切换后端不再改动这些调用点。
- **槽位 VM**：每个槽位一台，运行该槽位的全部 CLI 进程，包括对话、模型列表、额度查询和登录。同一账号因此始终出现在同一台机器、同一个出口上。主机名和 machine ID 由 Hub 为槽位生成并保存，重建虚拟机后保持不变；固定地址决定网关为它选择的出口，见[按来源绑定出口](#按来源绑定出口)。
- **用户工作区容器**：每个用户一个 LXC 容器，只运行该用户的 Mutagen 守护进程、同步屏障的执行进程，以及本机项目变更面板用到的只读 Git 查询，不运行智能体，所以不需要独立内核。Git 查询放在这里而不是宿主机，是因为智能体能修改仓库的 Git 配置，而配置可以指定要执行的命令；这些命令最多只能在容器内运行。容器使用独立的 uid 范围（`security.idmap.isolated`），与其他工作区和 Hub 的用户互不重叠；目录通过 idmapped 挂载（`shift=true`）绑定进去，写入的文件在宿主机上属于 Hub 用户。与虚拟机相比，它没有 virtiofs 进程，扫描目录是本机文件系统的速度，几秒内启动，内存只占几十 MiB，也没有设备端口上限；与宿主机共享内核，槽位 VM 写入的文件也能立即触发它的变更通知。默认不绑定出口，只能访问直连名单中的开发机。
- **网关保持虚拟机**：网关直接面对公网（Nginx、端口映射），并持有代理节点和证书的密钥。容器与宿主机共享内核，一旦网关被攻破，内核漏洞就能直通宿主机上的全部数据，因此不改为容器。它只有一台，改成容器约能省下 0.5 GiB 内存。
- **同步屏障**：智能体在槽位 VM 中执行远程命令时，`remote-shell` 连接本机的中继进程，中继经 `lxc exec` 的标准输入输出把请求交给 Hub；Hub 持有项目命令锁，并让该用户工作区容器中的常驻进程执行 `mutagen sync flush`。虚拟机之间不开放网络。命令异常退出时连接断开，Hub 随即释放锁。
- 目录在虚拟机内挂载到与宿主机相同的绝对路径，数据库记录和原生会话路径不需要转换。
- Claude 的审批 Hook 走 CLI 的标准输入输出（见[与智能体对话](agents.md)），不需要从虚拟机连回宿主机。
- **本机项目**：管理员「本机开发机」上的项目同样在槽位 VM 中运行 CLI，项目目录通过 virtiofs 挂载到相同的绝对路径，不创建镜像，也不经过同步。账号因此只有一种身份和一个出口。见[本机项目](#本机项目)。
- **网页终端**：本机项目的网页终端按设计仍是宿主机 Shell，拥有 Hub 用户的全部权限。在其中手动运行 CLI 时，账号会显示宿主机的身份。
- 每次运行在虚拟机内有独立的 cgroup，由 Hub 随命令传入的脚本创建，再降权到普通用户。暂停用 cgroup 冻结，结束时回收整棵进程树；客户端被强杀后遗留的进程组在下次检查时回收。ssh、同步屏障执行期间不会冻结。

## 本机项目

数据、环境文件、发布备份和 Hub 的运行目录都放在项目目录之外，因为项目目录会整个挂载进虚拟机：

| 内容 | 默认位置 | 修改方式 |
| --- | --- | --- |
| 数据目录 | `~/.local/share/clinavat` | `CLINAVAT_DATA_DIR` |
| 环境文件 | `~/.config/clinavat/hub.env` | `CLINAVAT_ENV_FILE` |
| 发布备份 | `~/.local/state/clinavat/releases` | `CLINAVAT_RELEASE_DIR` |
| 运行目录 | `~/.local/lib/clinavat` | `CLINAVAT_INSTALL_DIR` |

- **挂载白名单**：本机项目目录要加入 LXD 项目的 `restricted.devices.disk.paths`（`prepare-containers --local-root <目录>`），否则启动对话时会报错。
- **防护**：虚拟机模式下，Hub 拒绝使用包含或位于数据目录、环境文件目录、发布备份目录、运行目录、项目镜像目录、`~/.ssh`、`~/snap`（LXD 客户端私钥）、`~/.claude`、`~/.codex` 的本机项目。

**代价：**

- **速度**：virtiofs 比本机文件系统慢。实测 `git status` 约 0.6 秒（本机 26 毫秒），`tsc` 约 20 秒（本机 7 秒）。
- **内存**：槽位 VM 默认 1.5 GiB，同时运行 CLI 和大型构建可能不够。可以单独调高：`sudo lxc config set <实例> limits.memory=3GiB --project clinavat`，再重启该实例，并注意项目配额。
- **变更通知**：在宿主机上修改文件，虚拟机内的 `tsc --watch`、vite 这类工具收不到通知。
- **宿主机工具**：智能体用不了 `systemctl`、`lxc`、`sudo` 和宿主机的 SSH 密钥。部署和运维操作要在网页终端或服务器上执行。
- **依赖**：虚拟机与宿主机共用 `node_modules`。系统版本不同时，一边安装的原生模块可能在另一边无法加载。

**隔离的边界：** 智能体对项目目录有写权限，包括源码、`node_modules`、`.git/hooks`、`.git/config` 和 `deploy/` 脚本。Hub 从运行目录启动，所以这些修改不会在重启时生效。但只要在宿主机上用这个目录运行了命令，它们就会以 Hub 用户身份执行。开发 Clinavat 自身时要注意：

- **发布**：审查提交后，用运行目录里的脚本从提交构建，见[不中断任务的发布](deployment.md#不中断任务的发布)。不要在宿主机上的工作区里运行 `npm`、`git commit`、`git status` 或 `deploy/` 脚本。
- **需要 root 的脚本**：同样使用运行目录里的副本，例如 `sudo ~/.local/lib/clinavat/deploy/lxd/egress-bindings.sh`，不要用 `sudo` 运行项目目录里的脚本。

## 隔离边界

| 内容 | 是否隔离 |
| --- | --- |
| 其他用户的 workspace、会话数据、SSH 私钥 | 隔离：只挂载进本人的工作区容器，以及本人正在租用的槽位 VM |
| 工作区容器与宿主机 | 共享内核，以独立 uid 范围的非特权容器运行；其中只有同步程序和 Git 查询。恶意开发机或被改过的 Git 配置可以在容器内运行代码，但还要再利用内核漏洞才能越过这一层 |
| 同一槽位 VM 中上一位用户留下的内容 | 清除：换人时结束上一位用户的全部进程，卸载其目录，清空 /tmp、/var/tmp、/dev/shm、虚拟机内的家目录和 SSH 连接复用目录；智能体没有 root，无法在其他位置留下内容 |
| Hub 的数据库、`.env`、主密钥 | 隔离：项目策略禁止挂载这些路径 |
| 宿主机和内网 | 隔离：出站规则只放行公网和列出的开发机地址 |
| 其他用户的虚拟机 | 隔离：网卡端口隔离，并过滤 MAC 和 IP |
| **用户正在租用的共享槽位的账号令牌** | **不隔离**，见下文 |

### 共享槽位凭据

CLI 必须读取槽位的 OAuth 凭据才能工作，所以槽位目录始终挂载在槽位 VM 中，租用者的智能体可以读到账号令牌，包括刷新令牌。换人时会清理槽位 VM，但上一位租用者可能已经保留了副本。

**当前决定：接受这一点。** 运维要求：

- 只把槽位授权给可信用户。
- 撤销某用户的槽位授权后，重新登录该槽位，让旧令牌失效。
- 租用者也能改写槽位里的凭据文件。把它换成自己的账号后，下一位租用者的对话就会发到该账号。这同样依赖"槽位只授权给可信用户"。

### 进阶路线：令牌只留在宿主机

由宿主机上的代理代发模型 API 请求，虚拟机里只有无实际权限的占位凭据。以下内容均未验证，开工前逐项确认：

1. **可行性调研**
   - Claude Code、Codex 能否把模型请求指向自定义地址，同时继续使用订阅账号的 OAuth。
   - CLI 还会直接访问哪些接口（登录刷新、额度、遥测），这些请求如何处理。
   - 账号的服务条款是否允许这种转发。**如不允许，这条路线终止。**
2. **代理原型**：宿主机服务持有令牌并负责刷新，只转发白名单内的上游接口；额度事件和流式响应保持原样。
3. **访问控制**：虚拟机只能通过专用入口访问代理，由 IP 过滤确定来源虚拟机，再用每次运行签发的短期令牌确认会话和槽位租约。租约结束即失效。
4. **切换**：槽位目录不再保存真实凭据；用量探测改由代理完成。

代理会成为新的高价值目标，也会影响所有模型请求的可用性，需要单独设计其高可用和审计。

## Hub 操作共享目录的规则

虚拟机可以在共享目录中创建任意符号链接和特殊文件。这些链接在虚拟机内解析时逃不出共享目录，但 Hub 在宿主机上操作同一目录时，如果跟随链接就可能读写其他用户的数据。规则：

- **读取**用 `runtime/contained-files.ts` 的 `openContained`：非阻塞打开后，从文件描述符读回真实路径再校验，检查和读取之间没有竞争窗口，命名管道也不会卡住 Hub。工作区文件的预览、下载、列表和凭据读取都走它。
- **写入**用先写临时文件再改名的方式，并拒绝符号链接目录。
- **槽位的保存和恢复**在卸载之后进行，此时虚拟机改不了目录；移动文件用 `rename`，不跟随链接。
- **Hub 需要读回的文件**（SSH 配置、运行时密钥）只读挂载。
- **不解析共享目录中的复杂格式**：槽位里残留的 SQLite 文件直接归档，不打开。
- **绝不在宿主机上执行来自共享目录的文件。**

新增操作共享目录的代码时，都要按这些规则检查。

## LXD 基础环境

以 root 执行一次（参数含义见脚本开头的注释）：

```bash
sudo deploy/lxd/setup.sh --storage lvm:<卷组>/<精简池> --hub-user <Hub 用户> \
  --data-dir <数据目录> --workspace-dir /var/tmp/clinavat-workspace \
  --allow <开发机内网地址>/32:tcp:22
```

- 使用已有卷组时，先手动建好精简池：`lvcreate --type thin-pool -L 40G -n clinavat-thin <卷组>`。
- 脚本把 LXD 的两个 socket 都收回给 root。**`lxd` 组成员等同于 root**，智能体命令又以 Hub 用户运行，所以 Hub 用户不能留在这个组里。此后管理 LXD 需要 `sudo lxc`。
- 脚本结束时打印一条 `lxc remote add` 命令，以 Hub 用户执行。snap 版 `lxc` 固定把客户端证书放在 `~/snap/lxd/common/config`，备份数据目录时要一起备份。
- 调用 `lxc launch` 时必须关闭标准输入（`</dev/null`），否则它会一直等待从标准输入读取配置。
- 创建虚拟机时要带上 `raw.idmap`，它只能在关机状态下设置。`LxdExecutionHost` 创建时会自动带上。

## 虚拟机镜像

以 Hub 用户运行，不需要 root：

```bash
deploy/lxd/build-image.sh                    # 槽位 VM 镜像 clinavat-agent
deploy/lxd/build-image.sh --kind workspace   # 工作区容器镜像 clinavat-workspace
```

工作区镜像只有 Mutagen、SSH 客户端、Python 和时区数据，几分钟即可构建。构建机使用固定地址 `10.31.0.9`（`--address`）；虚拟机网段不再做地址转换后，需要在「网关 → 出口绑定」中为「镜像构建」绑定节点，迁移脚本会自动绑定。

整个过程约 15 分钟。发布很慢，可以用 `--builder <名称> --stage provision` 和 `--stage publish` 分两步。镜像包含官方 CLI、Mutagen、Git、ripgrep、bubblewrap，版本取自环境变量 `CLAUDE_CODE_VERSION`、`CODEX_VERSION`、`MUTAGEN_VERSION`、`NODE_VERSION`。

镜像里只有一个普通用户（uid、gid 与 Hub 相同），没有 sudo、cloud-init 和任何 setuid 程序。放开了 `kernel.apparmor_restrict_unprivileged_userns`，因为 Codex 的沙箱依赖 bubblewrap，隔离边界由虚拟机本身提供。

虚拟机内的进程使用与 Hub 相同的时区（Hub 的 `TZ`，未设置时取宿主机时区），同一账号无论在宿主机还是虚拟机上运行，CLI 看到的时区都一致。旧镜像没有时区数据，需要重新构建后才生效。

升级 CLI 时重新构建镜像。已有的用户虚拟机不会自动更新，需要删除后由 Hub 重新创建（数据都在宿主机上，不会丢失）。

## 已验证的行为

在嵌套虚拟化环境（LXD 6.10、virtiofsd 1.13、内核 7.0）中实测：

| 项目 | 结果 |
| --- | --- |
| 受限证书 | 只能操作 `clinavat` 项目 |
| 项目策略 | 拒绝 `raw.qemu`、proxy 设备、白名单外的路径、`../` 穿越和指向外部的符号链接挂载源 |
| 挂载 | 配置 `raw.idmap` 后可直接挂载权限为 700 的目录，运行中热插拔约 2 秒 |
| uid 映射 | virtiofsd 以 nobody 运行，只映射 Hub uid；虚拟机 root 对应宿主机 nobody |
| 虚拟机 root 写入 | 造不出 root 属主的文件，不能创建设备文件 |
| `security.capability` | 拒绝设置 |
| 文件系统能力 | `flock` 和 Unix socket 正常，可满足 Mutagen 需要 |
| `lxc exec` | 标准输入输出、环境变量、工作目录、退出码正常；SIGTERM 能转发；客户端被杀后虚拟机内进程随之结束 |
| 暂停 | 虚拟机内 cgroup v2 冻结和解冻正常 |
| 运行中卸载 | 进程占用时也能卸载，约 1 秒 |
| 网络 | 虚拟机之间不通，伪造源 IP 无法出网，访问不到宿主机和内网 |
| 槽位交接 | 仍挂载在别的虚拟机时拒绝交接，Hub 重启后依然生效；撤销后连已打开文件的进程也读不到（按用户分虚拟机时验证；改为槽位 VM 后，换人时的清理尚待真实环境验收） |
| 官方 CLI | Claude 控制协议和 Codex app-server 通过 `lxc exec` 完成真实账号对话、审批和原生会话恢复 |
| 文件竞争 | 4 秒内约 1.8 万次把文件换成指向机密的符号链接，Hub 没有一次返回机密内容 |
| 出口 | 经过网关代理；按来源绑定后由网关按虚拟机地址选择节点 |

已知限制：

- 虚拟机内的 Hub uid 能造出 setuid 为 Hub 用户的文件。目录权限是 700，只有 Hub 用户能接触到，不构成提权。
- 虚拟机 root 能留下 nobody 属主的文件，Hub 可能无法读取或删除。CLI 以无 sudo 的普通用户运行，正常情况下拿不到虚拟机 root。
- 首次创建虚拟机约 2.5～4 分钟，之后开机到可用约 50 秒（其中系统启动约 24 秒，其余主要是固件），每次 `lxc exec` 约 1 秒。这些数字取决于存储和是否嵌套虚拟化。
- 空闲虚拟机占用约 250 MiB，加上 CLI 进程。
- 槽位 VM 默认每台 1.5 GiB、2 个 vCPU；工作区容器默认上限 512 MiB，实际占用通常只有几十 MiB。见下文[容量与默认值](#容量与默认值)。
- 每台虚拟机的每个挂载都有一个 virtiofsd 进程。在实测中，Mutagen 扫描大目录时它们单个可占到 1 GiB；改为容器后，工作区不再有这部分开销。
- 每个挂载占一个设备端口，端口数上限 32。槽位 VM 固定占槽位目录和额度查询目录，租用者再占 4 个，其余是该用户正在使用的项目；同一用户大约可以同时使用 20 多个项目。
- 同一用户在槽位 VM 之间切换不需要重新挂载；换另一位用户时清理和卸载需要几秒到十几秒。

## 容量与默认值

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `CLINAVAT_VM_START_TIMEOUT_MS` | 15 分钟 | 单台虚拟机创建或开机的等待上限。开机全局排队，一次只进行一台，所以从轮到它时才开始计时，用户多也不需要调大；存储很慢时才需要调高 |
| `CLINAVAT_VM_BUS_PORTS` | 32 | 每台虚拟机的设备端口数（`limits.max_bus_ports`）。LXD 默认只有 8 个，放不下多个项目。新虚拟机创建时带上，已有虚拟机下次开机时自动补齐；运行中的虚拟机改不了，要重启才生效 |
| `CLINAVAT_VM_ADDRESSES` | `10.31.0.10-10.31.0.199` | 分配给槽位 VM 和工作区容器的固定地址范围，须在虚拟机网段内，并避开 DHCP 动态范围（迁移脚本默认设为 `.200-.254`） |
| `CLINAVAT_WORKSPACE_MEMORY` | `512MiB` | 工作区容器的内存上限，只在创建时生效 |
| `CLINAVAT_LXD_WORKSPACE_IMAGE` | `clinavat-workspace` | 工作区容器镜像 |
| `CLINAVAT_IMAGE_BUILDER_ADDRESS` | `10.31.0.9` | 镜像构建机的固定地址，须在虚拟机网段内、`CLINAVAT_VM_ADDRESSES` 之外，与 `build-image.sh --address` 一致 |
| 项目配额 | `setup.sh --max-vms 8 --max-users 32` | `limits.virtual-machines` 取槽位数上限，`limits.containers` 取用户数上限，`limits.cpu` 取虚拟机数的 2 倍，`limits.memory` 取本机内存的 75%。配额按**所有已创建**的实例计算，包括已关机的。项目只接受独立 uid 范围的容器（`restricted.containers.privilege=isolated`） |

配额按配置的上限计算，而不是实际占用：每个槽位 VM 计 2 个 vCPU 和 1.5 GiB，每个工作区容器计 1 个 vCPU 和 512 MiB，构建镜像时构建机再临时占一份。粗略估算：

```text
vCPU    = 2 × 槽位数 + 1 × 有项目的用户数 + 2（构建）
内存    = 1.5 GiB × 槽位数 + 0.5 GiB × 有项目的用户数 + 1.5 GiB（构建）
虚拟机  = 槽位数 + 1（构建）
容器    = 有项目的用户数 + 1（构建工作区镜像）
```

虚拟机实际会用满分到的内存，每个挂载还有一个 virtiofsd 进程，所以内存上限要按本机内存留足余量，不能只看 vCPU。

虚拟机数量超过配额时，新用户的虚拟机创建会失败，错误信息会说明要调哪一项。加内存后要记得调配额：

```bash
sudo lxc project set clinavat limits.memory=<本机内存的 75%> limits.cpu=<虚拟机数×2> limits.virtual-machines=<虚拟机数>
```

重新运行 `setup.sh` 也会按当前机器重新计算。

## 网关虚拟机

把上游网关迁到本机的一台虚拟机里，地址和 MAC 都沿用旧网关，所以宿主机路由、Hub 配置和防泄漏规则都不用改：

```text
外网 ─ 第二张网卡（宿主机不配地址）─ macvlan ─ 网关 VM eth0（原 WAN 地址和 MAC）
                                              网关 VM eth1（原 LAN 地址和 MAC）
                                                    │ 网桥 clinavat-lan
                                              宿主机（原地址）─ 用户 VM（NAT）
```

网关虚拟机在独立的 LXD 项目 `clinavat-gateway` 中，Hub 的受限证书访问不到。Hub 仍通过 SSH 强制命令管理它，SSH 主机密钥沿用旧网关的，指纹校验不受影响。

**第二张网卡上绝不能有宿主机地址。** 这张网卡直通外网，一旦宿主机在上面拿到地址（包括 IPv6 自动配置），流量就会绕开网关，用真实 IP 出站。加上网卡后立即禁用自动配置：

```bash
sudo tee /etc/systemd/network/10-<网卡>-wan.network >/dev/null <<'NETWORK'
[Match]
Name=<网卡>

[Link]
RequiredForOnline=no

[Network]
DHCP=no
IPv6AcceptRA=no
LinkLocalAddressing=no
NETWORK
sudo networkctl reload && sudo networkctl reconfigure <网卡>
```

**准备**（不影响线上流量，约 15 分钟）：先给运行脚本的用户配好登录旧网关 root 的 SSH 密钥。

```bash
sudo deploy/lxd/gateway-vm.sh prepare --old root@<旧网关> --ssh-user <用户> --wan-if <网卡>
```

脚本会先用随机 MAC 验证 macvlan 流量能穿过上层网桥，再安装、迁移配置，并用 `sing-box check`、`nft -c`、`nginx -t` 校验。中途失败时，删除虚拟机后重跑：`sudo lxc delete clinavat-gateway --force --project clinavat-gateway`。

准备之后如果改了脚本或配置，用 `gateway-vm.sh refresh` 更新已准备好的虚拟机，再用 `gateway-vm.sh diagnose --report <文件>` 检查。这两个命令都把 WAN 口临时接到空网桥上，不影响线上。

**切换**（公开站点和所有对话会中断几分钟）：**在上层虚拟化平台的控制台运行**，切换期间经网关的 SSH 会断开。

```bash
sudo deploy/lxd/gateway-vm.sh cutover --old root@<旧网关> --ssh-user <用户> --host-address <宿主机地址/掩码> --gateway <网关 LAN 地址>
```

脚本依次：挂上 10 分钟后自动回滚的定时器 → 让旧网关的 WAN 口下线 → 启动网关虚拟机 → 同步最新状态 → 把宿主机地址移到网桥 → 激活并做健康检查 → 等你输入 `yes`。超时、输入其他内容、任何一步失败或控制台掉线，都会自动恢复原状。

网关虚拟机的网卡固定命名为 `wan0`、`lan0`。不能用 `eth0`、`eth1`：内核按探测顺序分配这两个名字，互换会失败，配置和防泄漏规则都会接反。脚本在移动宿主机地址之前会核对 MAC 和地址。

**回滚**：确认前自动进行；确认之后，只要旧网关还在，可以手动执行 `gateway-vm.sh rollback`（参数同上）。如果旧网关连不上，就从平台控制台重启它。

**确认后：**

1. **立刻在平台上关掉旧网关并取消它的开机自启。** 它和新网关的 WAN 地址相同，重启后会冲突。
2. 验证一段时间后删除旧网关，并移除宿主机的第一张网卡（它已经不再使用）。
3. 清理 `authorized_keys` 中临时添加的管理密钥。
4. 确认管理面板能连上网关。

## 按来源绑定出口

网关只有一个 WAN 地址，但可以同时加载多个远端代理节点，并按流量的来源地址选择节点：

```text
号池机 10.10.10.10 ──┐
槽位 VM 10.31.0.x ───┼─ 网关 VM ─ 按来源选节点 ─ 代理 A / 代理 B / …
工作区容器 10.31.0.y ─┘            └─ 直连名单中的开发机
```

- **来源地址**：虚拟机网桥不再做地址转换，网关看到的就是虚拟机自己的固定地址；网关有回到虚拟机网段的路由。虚拟机网卡开启了 MAC 和 IP 过滤，不能冒用其他虚拟机的地址。
- **选择器**：网关为号池机和虚拟机网段内的每个地址各生成一个选择器，默认指向一个只能连到网关自身回环地址的死路出口 `unbound`。绑定或切换节点只是在运行时切换选择器，不改配置、不重启 sing-box，也不影响其他来源的连接。
- **已有连接**：切换后，已有连接默认继续使用原节点，直到它们自然结束；切换时勾选「中断已有连接」，则立即关闭该来源的现有连接。
- **DNS**：网关拦截经过它的 DNS 请求，按来源地址经同一节点解析。虚拟机的 DNS 指向公网解析器（默认 `1.1.1.1`），号池机已有的公网解析器同样由网关回答。
- **未绑定与失败**：按来源绑定后，号池机和虚拟机网段中未绑定的地址既不能访问外网，也不能解析域名；节点失败时保持断网，不会改用其他节点或直连。网关自身的流量（健康检查、证书）仍经共享的节点选择器。
- **直连**：开发机直连名单不经代理，对所有来源生效。端口映射（2222、8080 等）不受影响。

管理面板「网关 → 出口绑定」列出号池机、每个槽位和每个用户的工作区，可以分别选择节点。槽位在创建后即分配地址，可以在首次登录前绑定；未绑定的槽位不能开始对话。

### 迁移

迁移期间不运行任何 CLI：先停止 Hub，脚本确认服务已停止后才改动网络和移动数据。

1. 准备工作区容器：`sudo deploy/lxd/egress-bindings.sh prepare-containers --hub-user <Hub 用户> --max-users <容器上限>`。它设置容器配额，要求容器使用独立 uid 范围，允许挂载额度查询目录，并创建容器专用的 `workspace` 配置（1 个 vCPU、512 MiB、4 GiB 根盘、与虚拟机相同的网卡过滤）。默认配置中有只适用于虚拟机的设备端口设置，所以容器不使用它。
2. 以 Hub 用户构建两个镜像：`deploy/lxd/build-image.sh` 和 `deploy/lxd/build-image.sh --kind workspace`。此时网桥仍在做地址转换，构建机可以直接联网。
3. 构建新版本的后端和前端，然后停止服务：`npm run build && npm run host:stop`。这是第一次安装运行目录，要从审查过的工作区运行；之后的更新都从提交构建。
4. 删除旧的按用户虚拟机。它们还挂载着旧的数据路径，数据都在宿主机上，不会丢失：

   ```bash
   sudo deploy/lxd/egress-bindings.sh remove-old-machines --hub-user <Hub 用户>
   ```

5. 以 Hub 用户把数据移出项目目录：`node deploy/relocate-data.mjs apply`。脚本确认服务已停止、没有未结束的租约、没有实例挂载数据目录后，移动数据目录、环境文件和发布备份，并改写数据库和配置中的路径。中途失败会自动恢复；事后可用 `node deploy/relocate-data.mjs rollback` 撤销。`.releases/experiments` 是开发脚手架，留在项目内。
6. 更新挂载白名单：

   ```bash
   sudo deploy/lxd/egress-bindings.sh prepare-containers --hub-user <Hub 用户> --max-users <容器上限> \
     --data-dir <新数据目录> --local-root <本机项目目录>
   ```

7. 检查并执行（检查会用 Hub 的受限客户端创建一个临时容器，确认项目接受独立 uid 范围和 idmapped 挂载、写入的文件属于 Hub 用户，然后删除）：

   ```bash
   sudo deploy/lxd/egress-bindings.sh check --hub-user <Hub 用户>
   sudo deploy/lxd/egress-bindings.sh apply --hub-user <Hub 用户>
   ```

   `apply` 依次执行：
   1. 备份网关配置、宿主机网络和 LXD 设置。
   2. 更新网关控制器，并让 sing-box 启动后按状态恢复绑定。
   3. 为网关添加到虚拟机网段的路由，并声明虚拟机网段。
   4. 关闭虚拟机网桥的地址转换，把 DHCP 动态范围缩到 `.200-.254`，把虚拟机的 DNS 指向 `1.1.1.1`。脚本不改动宿主机自身的路由和 DNS，并在宿主机不是只经网关出站时拒绝执行。
   5. 把号池机和镜像构建地址绑定到当前节点（可用 `--node <节点>` 指定），然后切换到按来源绑定。
   6. 验证号池机的出口与节点一致、域名解析正常、网关健康检查通过。
8. 以 Hub 用户安装到运行目录并启动服务：`npm run host:install`。它先组装好 `~/.local/lib/clinavat`（需要联网安装运行依赖），再切换服务，失败时恢复原状。
9. 在「网关 → 出口绑定」中为每个槽位选择节点，就可以继续对话。

**不需要重新登录。** 登录状态是槽位目录里的文件（`.claude/.credentials.json`、`.codex/auth.json`），随数据目录移动，槽位 VM 挂载的就是这个目录；第 5 步会核对文件的大小和修改时间并列出结果。迁移时旧虚拟机已删除、Hub 已停止，不会有两处同时使用同一个令牌。CLI 自己保存的设备标识同样在这个目录内，因此也不变；只有主机名和 machine ID 会变一次，此后固定。

**绑定节点时选槽位现在使用的节点，让出口 IP 保持不变。** 如果要换节点，等迁移稳定后再逐个槽位调整，不要和这次迁移同时进行。

**回滚**：`sudo deploy/lxd/egress-bindings.sh rollback`。先切回共享节点，再恢复网关、宿主机网络和 LXD 设置。迁移后创建的虚拟机有固定地址，在共享模式下同样可用。

**全新安装**的顺序：`setup.sh`（本机项目目录用 `--local-root` 传入）→ 构建两个镜像 → `gateway-vm.sh prepare` 和 `cutover` → `egress-bindings.sh apply`。网关虚拟机的准备阶段依赖虚拟机网桥的地址转换，所以 `setup.sh` 仍先开启它，由迁移脚本关闭。

## 切换到虚拟机模式

运行中系统的切换由运维执行。**已在真实运行系统完成切换与验收。**

**切换前：**

1. 确认已运行 `deploy/lxd/setup.sh`，LXD 项目的挂载白名单指向当前的数据目录和 workspace 目录。
2. 确认 `--allow` 列出了所有 Hub 需要直连的内网开发机。经跳板机的项目只需要跳板机地址可达。
3. 确认镜像 `clinavat-agent` 已构建。
4. 确认[项目配额](#容量与默认值)够用：虚拟机数量至少等于需要运行的用户数。
5. 内存：每个活跃用户按 1.5 GiB 估算，再留出 Hub 和宿主机自身的用量。超过项目上限时需要调高 `limits.memory`、`limits.virtual-machines`，或给机器加内存。
6. 等系统空闲，完整备份数据目录。

**切换：**

```bash
echo 'CLINAVAT_EXECUTION_HOST=lxd' >> .env
npm run host:stop      # 同时结束宿主机上的 Mutagen 守护进程
npm run host:start
npm run host:logs
```

守护进程不能同时在宿主机和虚拟机上运行：它们用的是同一份同步数据，而文件锁跨不过 virtiofs。Hub 启动后会逐台开机恢复同步，首次创建每台要几分钟，用户多时排队时间相应变长。期间网站可用，相关操作会等待；日志里可以看到进度和错误。

如果切换前自行调整过配置，确认没有残留比默认值更低的 `CLINAVAT_VM_START_TIMEOUT_MS` 或 `limits.max_bus_ports`。

**验证：**用非管理员账号在 SSH 开发机项目上跑一轮 Claude 和一轮 Codex，覆盖审批、暂停和继续、停止、切换槽位、文件预览，确认同步状态正常、`/api/health` 的 `execution` 为 `vm`。

**回退：**删除 `.env` 中那一行，再执行 `host:stop` 和 `host:start`。同步数据和项目路径在两种模式下相同。回退前先停止虚拟机内的守护进程（`sudo lxc stop --all --project clinavat`）。
